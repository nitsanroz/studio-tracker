Read by any signed-in member, admin-only writes. **Optional**: without it everything except custom entries works, and both APIs degrade gracefully).
- `0021_harden_profile_writes` (**MUST BE APPLIED — privilege escalation.** `own profile update` had no `with check` and no column scoping, so any member could `update profiles set role='admin'` on their own row and inherit every admin-only table. Adds a BEFORE UPDATE trigger in the shape of 0011: members may change only `name`/`avatar_url`/`photo_url`. **Unlike 0011 it exempts the service role** (`auth.uid() is null`), because /api/avatar, /api/member-image and /api/admin/users write profiles with the service key after checking the caller's session.)
- `0022_links_notes_and_start_date` (**MUST BE APPLIED — applied by Nitsan 2026-08-06.** Adds the `links` table (titled reference links on a task OR a client, one owner enforced by a CHECK), `clients.notes`, and `tasks.start_date` (the left edge of a Timeline bar). ⚠️ **It also re-declares `enforce_task_member_columns` to add `start_date`** — 0011's trigger enumerates protected columns BY NAME, so any new task column is member-writable until it's named there, and without this a designer could re-schedule any task through the API. The app degrades gracefully without 0022 (the task select steps down a rung, `links` falls back to `[]`), but start dates and links can't be saved.)
- `0023_timeline_order_and_client_icon` (**MUST BE APPLIED.** `tasks.timeline_position` (a Timeline row order kept SEPARATE from `tasks.position`, which is per-section and drives the Tasks tab — sharing it would mean dragging a Timeline row could silently move the task into another section), plus `clients.icon` (a preset glyph name from CLIENT_ICONS) and `clients.icon_url` (an uploaded mark; wins over `icon`). ⚠️ **Re-declares `enforce_task_member_columns` again to add `timeline_position`** — see 0022 for why every new task column needs that. Degrades gracefully: the task select steps down a rung and clients render their initial.)
- `0024_task_types` (**MUST BE APPLIED.** `task_types` (name + colour + position, read-all/admin-write) seeded with the seven Nitsan named — Design, Wireframe, Content, Image making, Development, QA, Client side — plus `tasks.type_id` (FK, ON DELETE SET NULL). A task's KIND OF WORK, deliberately NOT the existing `tags`, which are workflow STATES ("in design", "Client approval", "Approved"); folding them together would force a task to say it's a QA job OR that it's awaiting approval, never both. ⚠️ `type_id` is deliberately ABSENT from the 0011 trigger's protected list — describing the work is collaborative like `tag_id`, unlike scheduling it. Degrades gracefully: task select steps down a rung, `task_types` falls back to `[]`, bars stay brand blue.)
- `0038_harden_time_entry_writes` (**MUST BE APPLIED — applied 2026-09-05.** `own time update` (0001) had no column scoping and `time_entries` had no trigger, unlike `tasks` (0011) and `profiles` (0021), so a member could rewrite EVERY column of their own rows. Two money-facing consequences: **0035's minutes bound was inert**, because its `legacy or …` escape — there for the recovery scripts — assumed `legacy` was not member-writable (`update({legacy:true, minutes:99999})` from the console passed the check), and `legacy` also decides which aggregates a row lands in, so flipping it hid a member's hours from Team/home while still billing the client; and the **Keys write-down**, the one place the studio reduces a bill, was gated on `isAdmin` in the component and nowhere else. The trigger lets a member change only `minutes`/`date`/`description` on their own NON-legacy rows — the DB half of `canEditEntry`. **Exempts the service role** like 0021, or the recovery scripts and the reversal SQL break.)
- **`data/*.sql` are NOT migrations and must never be numbered like them.** They are one-off data scripts the user runs in the SQL editor. Three of them used to be `0019_/0020_/0021_`, which collided head-on with `supabase/migrations/0019_estimated_entry_dates.sql` — Nitsan reasonably reported "I ran 0019" meaning the migration while the data file was still pending. They are now named for what they do: `data/task-titles-cleanup.sql`, `data/merge-clients-inreach-quadream.sql`, `data/finance-2016-import.sql`. Keep it that way.
- `0030_intake_revisions` (**APPLIED by Nitsan 2026-08-18.** `task_requests.answers_ack` (the client's answers AS THE STUDIO LAST ACKNOWLEDGED THEM) + `acked_at`, plus a partial index on `edited_at`. ⚠️ This is the reference point every "what changed" view is computed against — written when a brief is marked seen or approved, NEVER by a client edit, or the comparison it exists for would be erased. A brief needs review when `edited_at > acked_at`, one rule for every status. Nothing here touches `tasks`: a revision of an approved brief updates only the request row, and applying any of it to the task is an explicit action in the queue. Degrades gracefully — a null baseline reports "no earlier version was recorded" rather than a fake diff — but ⚠️ the WRITES need a `PGRST204` fallback or an unapplied migration breaks the seen receipt and approving.)
- `0029_intake_brief_reuse` (**APPLIED by Nitsan 2026-08-18.** `task_requests.edit_key` + `edited_at` + an index on the key, so a client can duplicate or edit a brief they sent. Two plain columns and nothing else: `task_requests` is admin-only for ALL operations under 0001's `admin all` policy and every public path is a service-role route, so there is no policy work and no 0011 trigger amendment (that trigger guards `tasks`). ⚠️ `edit_key` is an unguessable secret returned exactly ONCE at submit and never selected back out — the client's own browser is the only place it lives, which is what makes editing safe on a form anyone with the link can open. Degrades gracefully: without it the submission route steps down and inserts without the key, so the form works exactly as it did before and the feature stays dormant. ⚠️ That step-down is keyed on **PGRST204**, not 42703 — see the Deploy note.)
- `0028_intake_seen` (**APPLIED by Nitsan 2026-08-11.** `task_requests.seen_at` / `seen_by` / `client_notified_at`, for the "we've seen your brief" receipt. Three plain columns and nothing else: `task_requests` is admin-only for ALL operations under 0001's `admin all` policy, so there is no policy or trigger work here — and no 0011 trigger amendment, because that trigger guards `tasks`, not `task_requests`. Two stamps rather than one on purpose: a failed send must still leave the request marked as read. Degrades gracefully — before it is applied `mapTaskRequest` reads the missing keys as null, which renders as "nothing acknowledged yet", though `/api/intake/seen` itself 500s because the columns are in its select list.)
- `0037_client_keys_task` (**APPLIED by Nitsan 2026-09-01.** `clients.keys_task_id uuid references tasks(id) on delete set null` — the destination for hours written down before a client report. ⚠️ **CHOSEN, NEVER MATCHED BY NAME:** the real data holds `--- Keys ---` SEPARATOR tasks and two keys-shaped tasks still marked BILLABLE, so guessing from the title would eventually move hours onto a separator or onto a task that keeps billing the client. `on delete set null` rather than cascade — deleting a task must not take the client row with it. No policy work: `clients` already carries 0001's `admin all` plus the shared read policy, and the app writes it through the same admin-gated `updateClient` path as `hour_cap`/`report_notes`. Degrades gracefully — `mapClient` reads a missing column as null and `updateWithOptional` drops it from the write, so before it ran the Keys-task picker simply could not save and said so.)
